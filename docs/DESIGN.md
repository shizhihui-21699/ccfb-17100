# 短链与跳转服务安全改造 · 设计说明

> 目标:把"公司域名 + 短链"从**信任背书**变回**转发工具**。
> 本文说明每一项设计背后的取舍,以及为什么在"每天几千条、落地页多为合作方"的前提下这样取舍。

---

## 1. 问题的本质

事故里有两个独立缺陷,不能用同一招解决:

| 缺陷 | 本质 | 攻击者利用的信任 |
|---|---|---|
| 短链被用来发钓鱼 | 短链域名是公司的,收件人和反垃圾系统看到公司域名就放行 | **域名信任转移** |
| 业务页 `?redirect=` 可指向任意站点 | 开放重定向 | **公司页面的跳转能力** |

而"审核时放正常页、通过后换成钓鱼页"(approve-then-swap / TOCTOU)是**针对任何静态审核**的绕过手法。所以:

- **审核不能是"一次性盖章",必须是"带时效的结构指纹 + 持续比对"。**
- **创建时的结论不能直接被点击信任。** 每一次点击都要基于当前状态重新判断。

这两条决定了整体架构。任何"创建时打个 safe 标记、之后直接跳"的方案都会被这个攻击穿过,不论规则多精细。

---

## 2. 总体结构

```
                    ┌──────────────┐
  营销后台 ──POST──▶ │  创建 API     │ ① 廉价同步校验(不联网)
                    └──────┬───────┘   ② 结构风险打分
                           │            ③ 建 pending 记录 + 审计
                           ▼
                    ┌──────────────┐
                    │  存储/审计    │  hash-chain 审计日志
                    └──────┬───────┘
                           │
        ┌──────────────────┼───────────────────┐
        ▼                  ▼                   ▼
 ┌─────────────┐   ┌──────────────┐   ┌──────────────────┐
 │ 点击决策     │   │  巡检 Scanner │   │ 滥用响应          │
 │ (每次实时)   │   │  (异步,定时) │   │ 封禁/级联/追溯     │
 └──────┬──────┘   └──────┬───────┘   └──────────────────┘
        │                 │
        ▼                 ▼
 中转提示页 / 阻断    多探针抓取 + 指纹比对基线
```

代码对应:

| 目录 | 职责 |
|---|---|
| `internal/dest` | 建链时的**廉价**目标校验(无网络) |
| `internal/risk` | 风险打分(创建期 + 巡检期两套) |
| `internal/artifact` | 页面**结构指纹**与漂移比对 |
| `internal/htmlx` | 容错 HTML 解析,提取表单/跳转/外链 |
| `internal/probe` | 抓取器(防 SSRF / DNS rebinding / 体积炸弹) |
| `internal/service` | 编排:创建、点击决策、巡检、级联封禁 |
| `internal/saferedirect` | 业务页开放重定向的**白名单**修复 |
| `internal/audit` | 哈希链审计日志(可追溯、可验篡改) |
| `internal/httpapi` | 公开(跳转/中转页)与内部(管理)两套路由 |
| `cmd/shortlinkd` | 进程入口 + 巡检循环 |

## 3. 关键决策与取舍

### 3.1 创建时只做"廉价、不可跳过"的校验

**为什么不用"创建时就抓页面深度检测"?** 几千条/天,同步抓取会让建链从"点一下就出"变成"等十几秒",营销同事会绕开系统——绕过是这类项目最大的失败模式。所以:

- **同步**:URL 合法性、scheme、是否内网地址(SSRF)、是否公网短链服务、品牌词仿冒、punycode、开放重定向参数、创建人频率、活动域名离散度。全部是纯计算,毫秒级。
- **异步**:抓页面、提指纹、比基线。失败不影响建链,影响的是**能否被直接跳转**。

> 取舍:**建链速度优先**。安全压力后移到"点击时"和"巡检",这两处才是不影响营销体验的支点。

### 3.2 风险分只决定"是否自动化",不决定"是否可信"

这是全篇最重要的一条。

```
低分 ≠ 可信。低分只意味着"不需要人工介入",不代表"可以无声跳转"。
```

如果"低分就能直跳",那攻击者只要耐心等到审核队列清空、分数降下来,就得到"公司域名 → 钓鱼页"的效果——正是事故本身。所以:

- **是否直跳(`DirectRedirect`/`needsWall`)是独立于分数的严格判断。**
- **非一方的落地页,默认永远走中转提示页**(除非安全团队显式、持久地清除)。

代价:合作方落地页点击会多一步。这是**故意的**,并且可以用合作方白名单 + 显式 clearance 逐步降低(见 3.9)。

### 3.3 审批是"结构指纹快照",不是"布尔标记"

`artifact.Fingerprint` 记录的不是整页哈希(会被轮播广告/会话 token/AB 测试打爆),而是**结构性特征**:

- 表单提交到哪里(host + path)——钓鱼最核心的特征
- 是否有密码框、跨站表单
- `meta refresh` / JS 跳转目标 / iframe / 外部脚本来源
- 页面触及的**非一方注册域集合**
- TLS 是否有效、签发者

漂移比对 `artifact.Compare(baseline, live)`:

- **硬漂移**(触发隔离):密码框出现/消失、表单提交 host 变化、JS 跳转目标变化、第三方域集合变化、TLS 失效。
- **软漂移**(只记录):标题、正文哈希、外部脚本增删。

> 取舍:**不比对整页哈希**,否则真实营销页一改文案就误报。硬漂移锁定"行为是否变了",软漂移留给人工看。

### 3.4 基线用服务端密钥签名(HMAC)

`artifact.Sealed` = 指纹 + HMAC(服务端 `seal-key`)。巡检比对前**先验签**。

- 防止有人改存储里的基线指纹来"洗白"一个已被换内容的页面。
- `-seal-key` 缺省时随机生成并**大声警告**:重启后基线全部失效(退化为"重新扫一遍"),安全但不便利。生产必须配置。

### 3.5 抓取器按"攻击者控制 URL"来设计

巡检抓的是**外部、可能恶意**的 URL,所以 `probe` 做了:

- **DNS rebinding 防护**:自定义 `DialContext`,在**实际拨号时**再校验解析出的 IP,拒绝内网/回环/元数据地址。创建时校验过的域名,之后仍可能在 DNS 层改指内网。
- **手动跟随重定向**,每一跳都做同样校验,并限制跳数。
- **解压后限体积**(2 MiB),防 gzip 炸弹。
- **禁止走环境代理**。

> 为什么创建时不强制解析成功?合作方 staging 域名常常还没发布。创建时只在**解析成功且指向内网**时拒绝;其余交给巡检重试。

### 3.6 抗"给审核方看正常页"的多探针

单探针会被"按 UA / 按来源 / 按时间"做手脚。当前实现:

- 固定一组"巡检 UA",并对每个目标**串行限速**抓取(避免把合作方打成攻击)。
- 指纹的硬漂移(尤其**第三方域集合**、**外部脚本来源**变化)能抓住"同一 URL 开始加载钓鱼套件"。
- 巡检节奏随风险**自适应**:高风险 1 小时、低风险 24 小时、隔离后 72 小时。

> 已知盲区:**完全依赖 JS 在运行时才注入钓鱼内容**的页面,静态抓取看不到。缓解是:(a) 记录外部脚本来源集合,新来源算漂移;(b) 非一方目标**始终**有中转页,即使盲区里也拿不到"公司域名直跳"的效果;(c) 收件人举报回路(3.8)。真正要补可以加无头浏览器探针,但那是另一个复杂度量级,先不作为默认。

### 3.7 点击时**重新计算**,并识别"隔离/吊销"优先级

`service.Resolve` 每次点击都重新合并 `StructuralRisk` 与 `ScanRisk`,并且:

- **隔离(quarantined)优先于一切**:即使之后重扫"看着变好",也必须人工重新审批才能恢复。否则攻击者可以"钓一会儿再收手"骗过巡检。
- **吊销(revoked)立即生效**,点击直接 410。
- 未审批/未扫到基线 → 中转页。
- 一方且未强制 → 直跳。

### 3.8 中转页作为**第一类安全控件**

中转账页不是一个"你确定要离开吗"的礼节,而是针对"公司域名 = 可信"心理捷径的打断:

- 把**可注册主域**做成页面最醒目的元素(不是整条 URL——用户不读整条 URL)。
- 明确写出"该网站**并非**本公司运营",并声明"我们不会通过此页面索要密码/验证码/银行卡"。
- 非 HTTPS 明确警告。
- **不缓存**、`X-Frame-Options: DENY`、`frame-ancestors 'none'`、`Referrer-Policy: no-referrer`、严格 CSP——防止被套壳劫持或泄露目标。
- **"继续"是签名 token**,绑定 `code + target + 过期时间(10 分钟)`:
  - 不能被改写成别的目标;
  - 不能被复用到别的链接;
  - 过期失效;
  - 兑换时**再次**检查链接是否在期间被隔离/吊销。
- 页面上有**一键举报**,3 条独立举报自动隔离待审。

### 3.9 白名单:管"域名",不管"页面"

`risk.Domain` 白名单支持 `host` / `*.host` / 注册域,并可带**过期时间**。

- 命中 = "我们审过这个发布方",**不等于**"这个页面现在安全"。
- 一方域名(`FirstParty`)可以免中转;合作方域名仍需中转,除非安全团队显式清除 `ForceInterstitial`。
- 带 TTL 的白名单会自然过期,减少"审过一次就永久放行"的腐烂。

> 这直接回应"很多落地页是合作方的":合作方域名一次性入白,后续该域下所有短链都少一轮人工判断,但仍受巡检和漂移约束。

### 3.10 频率与"被钓鱼的营销账号"

真实场景里,钓鱼团伙常常是**盗用了营销同事的账号**来批量建链,而不是自己新注册账号。所以:

- **创建人小时配额**(默认 5000,远高于正常峰值,但能挡住脚本爆量)。
- **创建量突增**作为风险加分(账号被盗的典型形态)。
- **同一活动下域名过于离散**作为风险加分("春季大促"不该指向 20 个互不相关的域名)。
- 所有建链记录 `creator_id / dept / origin_ip / request_id / campaign`,直接进入审计链。

> 取舍:配额设得**高**。设低会误伤大促、逼人绕过;真正的保护是"突增"信号 + 事后级联封禁。

### 3.11 一键封禁 + 级联 + 可追溯

| 操作 | 作用范围 | 场景 |
|---|---|---|
| `Revoke(linkID)` | 单条,立即 410 | 个案 |
| `RevokeDomain(domain)` | 该注册域下**所有**活链 | 合作方域名被入侵——最快止血 |
| `RevokeCampaign(campaign)` | 一个活动全部 | 活动级事故 |
| `RevokeCreator(creatorID)` | 一个账号所有活链 | 账号被盗/内部人 |

封禁**必须带 reason**(API 强制),写入审计链,记录操作人与时间。

### 3.12 审计:哈希链,可验篡改

"追溯创建人"只有在**日志改不了**时才有意义。`internal/audit`:

- 每条 = `seq + payload + prev_hash`,hash 覆盖前一环,**改动/删除/重排任一条都会导致后续链断裂**。
- 支持落盘 + 重启**回放续链**(`Open`)。
- `Verify()` 全量校验;管理端有 `/api/audit/verify`。

> 诚实边界:这是**防篡改可发现(tamper-evident)**,不是防篡改(tamper-proof)。有写盘权限的人可以重算整条链。生产应把每条事件**同步推送到独立只写 sink**(WORM/SIEM),本地链用于对账。这一点在代码注释里也写明了。

### 3.13 第二个缺陷:业务页开放重定向

`internal/saferedirect` 用**纯白名单**替换"看起来像 URL 就放行":

- 允许:相对路径(限前缀)、同站/同 eTLD+1 的绝对 URL(限路径前缀)、白名单 host。
- 拒绝:`//evil.com`、`/\evil.com`、反斜杠、控制字符、`javascript:`/`data:`/`file:`、userinfo 混淆(`https://good@evil`)、后缀混淆(`good.com.evil.com`)、内网 IP。
- 不做任何"启发式放行"——历史上每一种启发式都被绕过过。

> 落地建议:业务代码里所有"读 `redirect`/`next`/`return` 参数"的地方,**统一收敛到这一个函数**,不要各写各的。

## 4. 状态机

```
             ┌─────────┐  首次扫描通过   ┌────────┐
  创建 ──────▶│ pending │───────────────▶│ active │
             └────┬────┘                └───┬────┘
                  │ 扫描高危                │ 硬漂移 / 高危 / 举报≥3
                  ▼                         ▼
             ┌───────────────────────────────────┐
             │          quarantined               │◀── 人工 Approve(重抓当前页 → 重置基线)
             └──────────────┬────────────────────┘
                            │ 运营/安全 Revoke
                            ▼
                       ┌──────────┐
                       │ revoked  │  (终态,点击 410)
                       └──────────┘
```

要点:

- `pending` 期间点击一律中转页;`pending` 不会因为"分数不高"就直跳。
- `quarantined` 是**人工闸门**;自动重扫不会解除,必须 `Approve`。
- `Approve` **强制重新抓取当前页**再评估——审批的是"此刻的页面",不是"工单打开时的页面"。

## 5. 为什么这样能挡住"先过审再换页"

| 攻击步骤 | 系统反应 |
|---|---|
| 建一条指向合作方的短链 | 廉价校验通过,进入 `pending`,立即入巡检 |
| 巡检抓到正常页 | 记指纹为**签名基线**,转 `active` |
| 客户点击(未显式清除前) | **中转页**,即使 `active` |
| 换成钓鱼页 | 下一次巡检:硬漂移(密码框/表单 host/第三方域)→ **隔离**;或客户点击时若已隔离 → **阻断** |
| 争分夺秒:换页发生在两次巡检之间 | 点击仍有中转页(非一方);收件人举报 3 条自动隔离;`RevokeDomain` 一键按域止血 |
| 想改基线洗白 | 基线有 HMAC,存储被改则验签失败 → 视为无基线 → 回到中转页 |
| 批量注册账号/盗号刷链 | 小时配额 + 突增信号 + 活动域名离散度 |
| 用业务页 `?redirect=` 洗白 | `saferedirect` 白名单直接拒 |

**残余风险**(诚实列出):

1. 巡检间隔内的窗口。缓解:中转页 + 举报 + 按域封禁,不靠"实时检测"。
2. 纯 JS 延迟注入。缓解同上;要根治需无头浏览器探针(默认不开,作为可选增强)。
3. 合作方**整站**被黑但页面结构不变(例如仅换后端收集地址)。缓解:表单 `action` host 变化属于硬漂移;若连 host 都不变则检测不到,依赖举报与外部情报。
4. HMAC 密钥泄露。基线失去完整性保证——按密钥管理事故处理。

## 6. 性能与容量

- **建链**:纯内存/纯计算 + 一次配额计数,亚毫秒级;可水平扩展(存储换 SQL)。
- **点击**:全内存决策,无外呼,可扛高 QPS;`Resolve` 不阻塞在扫描上。
- **巡检**:串行限速(默认每目标间隔),按风险自适应节奏;`-scan-batch` 控制每轮条数。规模大时可拆成独立 worker + 队列。
- **存储**:当前 `Memory` 实现与接口 `store.Store` 隔离,可直接换 SQL;`Query.DueBefore` 是巡检队列索引的挂点。

---

## 7. 部署要点

1. **管理 API 绝不与公网路由共用中间件**:必须挂在 SSO/mTLS 后(`-admin-addr` 默认 127.0.0.1)。
2. **`-seal-key` 必须配置**并纳入密钥管理;轮换需考虑存量基线。
3. **`-allow-private-net` 仅用于测试/CI**,生产开启即重新引入 SSRF。
4. **审计链**落盘 + 外推只写 sink;定期跑 `/api/audit/verify` 对账。
5. **白名单带 TTL** 录入,避免"审过即永久"。
6. 监控:`blocked_clicks`(拦截点击)、隔离数、巡检失败数、`quarantined` 存量。
7. **业务页跳转**:把所有 `redirect/next/return/...` 参数收敛到 `saferedirect.Resolve`。

## 8. 运行与验证

```bash
go test ./...          # 单元 + 端到端(含 approve-then-swap、token 伪造、开放重定向、审计篡改)
go run ./cmd/shortlinkd -h
./scripts/demo.sh      # 起真实 HTTP 服务,演示 正常→过审→换页→隔离→封禁→追溯 全链路
```

`scripts/demo.sh` 会启动一个真实的"合作方"站点(先正常页、后被切换成钓鱼页),展示:

1. 建链(pending + 中转页)
2. 巡检通过 → active + 基线
3. 换页 → 硬漂移(detected: `baseline_drift:has_password`)→ 隔离
4. 点击 410 阻断
5. `RevokeDomain` 一键按域封禁
6. 审计链按人追溯 + `verify` 通过
7. 仿冒域名建链被 422 拒绝

## 9. 如果继续做

- **SQL 存储 + 队列化的巡检 worker**(当前是单进程内存版,接口已隔离)。
- **无头浏览器探针**(应对 JS 延迟注入),作为高风险链接的加严路径。
- **外观相似域名检测**(同形字/编辑距离),补 `brand_lookalike` 的盲区。
- **接外部情报**(威胁情报域列表、证书透明度日志)做建链前快速否决。
- **中转页埋点**:统计"到达中转页但未继续"的比例,作为可疑信号回灌。
- **与短信/海报投放系统联动**:投放前强制过一遍风险评估,而不是只依赖事后巡检。
